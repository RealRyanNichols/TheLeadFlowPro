# Engine 7.2: Ads reporting

Status: built on a branch with fictional data. Live account connections
are off by a server switch and are a per-client approval. Pricing and
go-live are decisions 26 to 28 in `docs/decisions-needed.md`.

## What it is

A weekly, plain-English ads report for one client at a time: spend by
platform, leads by source from the client's own lead list, cost per lead,
the trace-the-sale chain (source → first action → outcome) against the
client's own records, and one recommended decision. It comes out as a
client-viewable page in HQ (`/hq/reports`) and an email draft stored next
to it. Definitions print on every report. There is no return-on-ad-spend
figure anywhere: spend and the value the client recorded on won leads sit
side by side and the report stops there.

## How a client's token is stored

The same way their text line's key is: one row per workspace in
`hq_connections` with kind `meta_ads` or `google_ads`, `config.account_id`
holding the ad account id, and the token in `secret_ciphertext`, AES-256-GCM
under the HQ key chain (`lib/hq/crypto.ts`). The browser role can read the
row's label and status, never the ciphertext. Adapters receive the token
for one request and return rows that never contain it. Two clients never
share a row, a token, or a report.

## Setup (per client, with approval)

1. The client owns the ad account. Ryan is added as a partner or manager
   on the client's Meta Business or Google Ads account; the client is never
   asked to hand over a personal login.
2. Meta: generate a system-user token scoped to `ads_read` on the client's
   ad account, under the client's Business. Store it with
   `upsertConnection(db, workspaceId, { kind: "meta_ads", label, config: { account_id: "act_..." }, secret })`
   from a server-side script or an admin action (none is exposed yet).
3. Google: needs a Google Ads developer token for The LeadFlow Pro
   (application, basic access) in `GOOGLE_ADS_DEVELOPER_TOKEN`, plus the
   client's OAuth refresh token. Until the developer token exists the
   adapter answers `not_configured`.
4. Set `ADS_LIVE_PROVIDERS=true` in Vercel (Ryan only). Everything above
   still returns `disabled` without it.

## Runbook: the weekly report

1. Pull: `syncPlatform(db, workspace, "meta", { start, end })` for the
   last 15 days, then `google` if connected. Rows upsert on
   (workspace, platform, account, campaign, date), so a re-run replaces,
   never doubles.
2. Build and store: `buildAndStoreReport(db, workspace, leads, now)`
   writes the report JSON and the email draft to `hq_ads_reports` for the
   week, status `draft`.
3. Read: the owner opens `/hq/reports`. The page builds the same report
   live from the same rows.
4. Send: not wired. Sending the email draft is a later step behind
   decision 27; when it exists it goes through `sendEmailOnBehalf` with a
   dedupe key of `ads_report:<workspace>:<week_start>` and never twice.

A cron entry for step 1 and 2 is intentionally absent until a client is
connected.

## What the report will and will not say

- Spend is what the platform reported. Leads are the client's records.
  Platform-reported leads are shown for comparison and named as such.
- Cost per lead prints only when the client's records show at least one
  lead from that platform.
- Prior-week figures print only when prior-week data exists.
- Won value prints only the number the client typed on the won lead.
- The decision comes from a fixed rule list, in order: unanswered ad leads
  first; spend with no tagged leads second; a platform-versus-records gap
  third; a cost-per-lead gap between platforms fourth (review, never move
  budget on one week); unrecorded won value fifth; otherwise hold.
- No ROAS, no multiples, no rankings, no guarantees. The test suite fails
  if those words appear.

## Limits

- Two platforms. TikTok, LinkedIn, and others are not adapters yet.
- Attribution is the client's own tagging (`source = meta`, or
  `utm_source` / `source_detail` naming the platform). An untagged form
  lead is not an ad lead, and the report says so rather than guessing.
- Campaign names on leads come from `utm_campaign`; a mismatch with the
  platform's campaign name shows as two campaign lines, not a merge.
- The Google adapter is written against v18 GAQL but has not run against a
  live account (no developer token).
- Currency is shown as reported; there is no conversion.
- The page has no date picker; it is always the last full week.

## Rollback

Revert the merge. If the migration was applied: drop `hq_ads_reports` and
`hq_ads_daily`, and restore the previous `hq_connections_kind_check`
(the four original kinds). Connection rows of the two new kinds must be
deleted first.
