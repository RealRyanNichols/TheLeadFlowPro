# Engine 7.6: Client scoreboards

Status: built on a branch. The three existing boards are unchanged in
public; each now carries a written opt-in record and a private owner
view reachable by a signed link. Pricing and go-live are decisions 36 and
37 in `docs/decisions-needed.md`.

## What it is

The scoreboard as a per-client feature with two faces:

- **Public board** (`/scoreboard/<slug>`): aggregate counts with the
  definitions block, listed on `/scoreboard`, the homepage, the metric
  roll-ups, and the sitemap only while the client's `optIn.publicBoard`
  is true. This is the proof system `/results` links to.
- **Owner view** (`/scoreboard/<slug>/owner?k=…`): the same feed plus what
  the public board withholds for that client (the payment-record count,
  the day-by-day 90-day table, a CSV of the aggregates, the capture-source
  breakdown) and a plain-English reading of the last 30 days against the
  30 before. Reached only by a signed link Ryan generates. Noindex, no
  storage, no sends.

Both read the same `scoreboard_public_daily` function on the client's own
Supabase project, which returns counts per day and nothing else. There is
no name, email, phone, or dollar figure in either view because the feed
does not carry them.

## Runbook: a client's board

1. **Opt-in in writing.** The client owner says yes to the public board,
   the owner view, or both, and to the payment-record count if it is to
   show. Record who and when.
2. **Feed.** Apply `scoreboard_public_daily` to the client's Supabase
   project. Existing sites: write it against their tables (see
   `docs/scoreboard.md`). Stack clients: `stack/schema/005_scoreboard.sql`.
   Grant execute to anon; it returns aggregates only.
3. **Registry.** Add the business to `SCOREBOARD_BUSINESSES` with the
   project URL, publishable key, `showSales`, `paymentSourceNote` (exact
   definition), `unsupportedMetrics` for anything the feed does not
   observe, and the `optIn` block. Add `SOURCE_NOTES` for the slug in
   `lib/scoreboardMetrics.ts` so every metric has its definition.
4. **Owner link.** `HQ_SECRET=… npm run scoreboard:owner-link -- --business <slug>`
   and send it to the owner directly. It is valid until the secret rotates
   or `optIn.ownerView` is turned off.
5. **Withdraw.** Flip `optIn.publicBoard` or `optIn.ownerView` to false.
   The board leaves the list, the sitemap, the homepage, and the roll-ups
   on the next deploy; the owner link 404s.

## Rules

- Real numbers or nothing. A feed that does not answer renders "Feed
  unavailable" on both views.
- Aggregate counts only. Never a name, contact, or dollar figure.
- Unsupported metrics render as "not tracked", never as zero.
- The reading compares counts and states what is missing; it never
  attributes a cause or promises a result.
- One flag withdraws a client from everywhere.

## Limits

- The owner link is a bearer key. Anyone with the link can read the
  owner view; there is no login. Rotate `HQ_SECRET` to revoke all links
  at once, or flip the flag for one client.
- One board per business; no roll-ups across a client's multiple sites.
- The stack feed's paid-lead rule is a source-name match on
  `people.first_source`; a client whose forms do not pass the source
  through will show ad-attributed leads as zero, which the definitions say.

Revert the merge. No data, no migration on this project.
