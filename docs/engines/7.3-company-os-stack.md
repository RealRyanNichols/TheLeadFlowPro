# Engine 7.3: White-label Company OS stack

Status: built on a branch as a library, schema, fictional demo, and
provisioning plan. Nothing deployed. Pricing and go-live are decisions 29
to 31 in `docs/decisions-needed.md`.

## What it is

The Company OS offer as one configurable stack instead of a rebuild per
client: a CRM with one record per person, follow-up sequences with consent
and stop conditions, a member portal, an owner dashboard, and payment
hooks. Each client gets their own copy in their own Supabase project, their
own Vercel project, and their own Stripe account. Separation is the
tenancy model: there is no shared database and no shared tenant column,
so one client's data cannot reach another by any query.

Delivery is a config file plus the provisioning plan the config generates.

## Files

| Path | Role |
| --- | --- |
| `stack/lib/config.ts` | `StackConfig` type and `validateStackConfig`. No imports. |
| `stack/lib/people.ts` | One record per person. Match by normalized phone, then email. Consent only rises through a form; STOP is global and one-way for automation. |
| `stack/lib/sequences.ts` | Enroll, decide each step at send time (consent, address, STOP, status, reply, quiet hours), dedupe keys, idempotent scheduler pass. |
| `stack/lib/payments.ts` | Stripe event ledger applied exactly once by event id. A redirect returns `pending_verification`. Failures become private owner actions. |
| `stack/lib/portal.ts` | The member view: their own rows only. Members may change only their own two consent flags. |
| `stack/lib/dashboard.ts` | Owner dashboard from counts of real rows. |
| `stack/lib/provision.ts` | `provisioningPlan(config)`: ordered steps, env names, migrations, checks; `envExample`; `ownershipList`. |
| `stack/schema/001_core.sql` … `004_payments.sql` | The client-side schema, module by module, RLS on every table. |
| `stack/clients/fixture-fitness-club.json` | The fictional demo client. |
| `scripts/stack-demo.ts` | `npm run stack:demo` runs the whole thing on fictional data; `-- --plan` prints the provisioning plan. |
| `tests/stack.test.ts` | Config, merge and consent, sequences and STOP, quiet hours, payments idempotency, portal isolation, dashboard, provisioning, schema shape. |

## Runbook: standing up a client

Run `npm run stack:demo -- --config stack/clients/<slug>.json --plan` and
follow the numbered steps it prints. In order:

1. Client creates their Supabase project (their org, their card). Ryan is
   a member, never the owner.
2. Apply `001_core.sql`, then the module files the config turns on.
3. Verify the client's sending domain with their email provider.
4. Sequences on: connect the client's own text line, confirm STOP works
   before any sequence is enabled.
5. Payments on: restricted Stripe key on the client's account, webhook
   with signature verification.
6. Client creates their Vercel project and sets every env name from the
   printed `.env.example` (names only) on a screen share.
7. Portal on: magic-link sign-in from the client's sender; test with two
   members that each sees only their own rows.
8. Domain at the client's DNS, HTTPS on.
9. Set `launch.status` to `live` with `scopeApprovedOn`; hand over the
   ownership list.

Every step has a check. Do not move to the next step until the check
passes.

## Rules the code enforces

- A person is one row. A second form with the same phone or email updates
  that row; it never creates a twin.
- A form can turn consent on. Only STOP, the owner, or the person in their
  portal can turn it off, and a form cannot undo a STOP.
- STOP is global: every channel, every sequence, immediately, and the
  person moves to `do_not_contact`. Automation cannot move them back.
- Every step is decided at send time. No consent, no address, STOP, a
  stop status, or a reply (when the sequence stops on reply) means no
  send. A step skipped for consent or address is skipped for good and the
  sequence moves on.
- Sends carry `seq:<enrollment>:<step>` as a unique key. A retried job
  cannot send a step twice.
- Quiet hours are enforced by shifting the send into the next window in
  the client's timezone.
- Nothing is marked paid from a browser redirect. Only a verified Stripe
  event moves the ledger, and each event id applies once.
- A failed payment is a private action for the owner, never a label the
  person sees.
- The portal shows a member their own rows only; RLS says the same thing
  in the database.

## Limits

- The stack is the library, schema, and plan. The deployable Next.js app
  around it (routes, forms, portal pages, cron) is the next build and is
  not on this branch.
- Message templates are ids in the config; the copy lives in a per-client
  templates file that goes through the copy rules before launch.
- Two channels. No voice, no push.
- One Stripe account per stack. No marketplace or split payments.
- No import tool yet. Existing customer lists are loaded by a one-off
  script through `upsertPerson` so the merge rules apply.

## Rollback

The stack lives in the client's accounts. Reverting a client is their
Vercel rollback plus, if needed, dropping the tables in their project. The
files on this branch revert with the merge.
