# Engine 7.9: SellerProof generator

Status: SellerProof already ships as a product (`docs/SELLERPROOF_RELEASE.md`):
structured intake, a formatted dispute-response packet, a fictional sample,
a paid export at the published price, and the "not legal advice" line on
every packet. This engine adds the generator layer under it, the
file-fingerprint step, and the completeness reading, and records the
pricing question as decision 42.

## What was already true

- Intake is structured: order and dispute references, amount, deadline,
  product type, description, statement, a timeline, and an evidence index
  typed as receipt, delivery, usage or access, customer messages, terms or
  policy, cancellation or refund, or other.
- Empty inputs render as labelled markers such as `[amount missing]` and
  are listed as gaps. Nothing is filled in.
- Original files are not uploaded. The seller attaches them in their
  provider's dashboard.
- Export is paid, verified against Stripe on the server, and never
  triggered by a redirect alone.

## What this engine adds

| Path | Role |
| --- | --- |
| `lib/sellerproof/generator.ts` | `assemblePacket` (six sections with a gap count each), `intakeCompleteness` (order, communications, delivery or use, policy), `attachmentManifest`, `readinessSummary`, `samplePacket`, `PREPARATION_NOTICE`. |
| `lib/sellerproof/packet.ts` | Optional `attached` metadata on an evidence item: name, size, type, SHA-256. Parsed and bounded; a forged hash is rejected. The draft prints the fingerprint next to the file to attach. |
| `lib/sellerproof/fingerprint.ts` | Browser-side SHA-256 of a file the seller picks. Only the metadata is kept; the bytes never leave the device through this tool. |
| `app/sellerproof/build/Builder.tsx` | "Fingerprint the original file (stays on your device)" on each evidence item. |
| `app/sellerproof/sample/route.ts` | Uses the shared fictional sample. |
| `scripts/sellerproof-demo.ts` | `npm run sellerproof:demo`: assembles the sample and an empty intake, prints both, writes the sample HTML to `build/sellerproof/`. |
| `tests/sellerproof-generator.test.ts` | Empty intake invents nothing; sample completeness is honest; attachments are metadata only; parsing rejects forged fingerprints; the product stays document preparation. |

## Why fingerprints instead of uploads

Ryan's brief says evidence is uploaded by the seller. Uploading the
originals through SellerProof would put customer records on this server
and in this database, which the product's privacy promise rules out, and
would still not submit anything to a processor. The fingerprint gives the
seller the useful part: the packet names the exact file, with its size
and hash, that goes with each evidence entry, so what they upload to the
provider matches what the packet describes. If Ryan wants real uploads,
that is decision 43 and a separate build with its own storage, retention,
and deletion rules.

## Rules the code enforces

- Every printed fact is seller-entered. Empty renders as `[… missing]`
  and is listed under "Missing before you submit".
- Completeness is a count of four intake areas, printed as such. It is
  not a prediction of the outcome and the copy says so.
- The disclaimer and the preparation notice are on every assembled
  packet.
- An attachment is name, size, type, and hash. A hash that is not 64 hex
  characters, or a size out of range, is refused at parse time.
- The rendered packet contains no `src`, `href`, or `data:` URIs.

## Limits

- One dispute per packet; no bulk mode.
- The four completeness areas are generic; a processor may ask for more
  or less.
- No processor integration, no AI drafting, no outcome scoring, by
  design.

## Rollback

Revert the merge. The `attached` field is optional, so existing drafts
and backups parse unchanged.
