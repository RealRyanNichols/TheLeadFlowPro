# Tool imagery and licensing

## The decision

Every image in the tool library is original artwork generated from the registry
by `lib/tools/art.ts`. No stock photography, no third-party illustration, no
hotlinked assets, no AI-generated raster images.

That was a deliberate choice over licensed stock:

- A library heading for 250 tools needs 250 relevant, correctly cropped images.
  Stock photography of people pointing at laptops is not relevant to a concrete
  calculator, and finding 250 that are would take longer than building the tools.
- Licence terms on stock vary per asset and per use, and an embed running on a
  customer's own website is a redistribution question nobody wants to answer per
  image.
- Generated SVG is a few kilobytes, is sharp at any size, has no layout shift
  because the dimensions are declared, and never needs a mobile crop.
- The tool type is legible at thumbnail size, which a photograph of an office
  never is.

The tradeoff is that the artwork is graphic rather than photographic. For a
catalogue of calculators that reads as a feature, not a compromise.

There are no third-party image assets in the tool library, so there is nothing to
attribute and nothing to re-license. If that ever changes, the asset, its source
URL, its licence and the date it was downloaded belong in the table above, and
the file belongs in the repository rather than being hotlinked.

## How the artwork is built

Every tool has one hand-authored scene illustration in `art/scenes/<slug>.svg`
— an original flat-vector composition of that tool's subject (the missed-call
phone, the buried-in-paperwork owner, the receipt fed by monthly bills), built
to the contract in `art/STYLE.md`: light ground, the six-gradient accent
family in fixed assignments, ink silhouettes, no text, no template skeletons.
The brief for each scene (concept, subject, composition, accent) lives in the
registry at `lib/tools/visuals.ts`.

`npm run art` publishes each scene to the two paths the site serves — card
`1200 × 675` and hero `1600 × 900`, the same 16:9 drawing at two declared
sizes — and fails if any published tool has no scene.

OG share cards are a separate system: designed per tool in the Figma file
"LeadFlow Tools — OG Cards" and rendered to `public/og/tools/<slug>.jpg`
(exactly `1200 × 630`) by `npm run og`.

## Regenerating and reviewing

```bash
npm run art                        # publish scenes to /public + manifest
node scripts/render-art.mjs --sheet   # contact sheet of all scenes
node scripts/render-art.mjs <slug>    # render one scene for review
node scripts/art-similarity.mjs       # fail if two scenes read as clones
```

`npm run art` is deterministic, only rewrites what changed, and deletes art
for tools that no longer exist, which stops a dead file quietly passing the
"file exists" check forever. Output is committed, and a manifest is written to
`public/tools-art/manifest.json` with per-file dimensions, byte size and a
content hash.

## What is validated

`npm run validate:tools` fails the build on any of:

- a published tool with no card or hero file on disk
- an SVG with no explicit width and height, which would cause layout shift
- dimensions that disagree with what the registry declares
- an aspect ratio that does not match the declared size
- card art under 1200 wide, hero art under 1600 wide
- a file under 250 bytes or over the 120 KB budget
- any remote URL inside an SVG
- missing alt text
- two unrelated tools with byte-identical artwork, which would mean the generator
  lost its per-tool variation

`tests/registry.test.ts` repeats these checks per tool so a failure names the
tool rather than the batch.

## Alt text

Generated by `toolArtAlt()`, describing the picture rather than repeating the
tool name, which the surrounding markup already provides. Decorative uses, such
as the thumbnails inside the tool finder, pass `alt=""` so a screen reader is not
made to read the same thing twice.
